## 2а. Телефоны и браузер

- **Браузерное демо** (`Web/`): та же симуляция, собранная Emscripten в WebAssembly, плюс запасная сборка на чистом JS
  для хостов, где WebAssembly запрещён. На телефоне доступно без установки. WebAssembly тратит 0,25–0,5 мс на тик,
  JS — около 1,9 мс (на десктопе).
- **Unreal под iOS и Android**: настройки упаковки, мобильный рендер, профили устройств, HUD с safe area и
  масштабом под пальцы. Реальная сборка на устройствах не проверялась: нужен движок, а для iOS ещё Mac.

## 3. Отступления и допущения

1. **Flow fields → A\*.** При 6 отрядах на сторону A* с перепрокладкой дешевле и проще.
   Flow fields понадобятся, когда отрядов станет больше 20 (рейды, Alliance War).
   Интерфейс движения от этого не зависит.
2. **Формат реплея: JSON вместо MessagePack.** Его удобно читать и сравнивать.
   Формат изолирован в `Replay.cpp`, заменить можно в M1 вместе с бэкендом.
3. **`titanVsTitanMult = 5`** (`rules.json`). Без этого множителя дуэль титанов шла около 120 с.
   С ним дуэль занимает около 32 с, что попадает в цель 25–40 с.
4. **HUD на Canvas (`AHUD`), не на UMG/CommonUI.** Так нет ни одного `.uasset`, и прототип собирается из чистого кода.
   В M1 интерфейс переносится на UMG и CommonUI с теми же действиями `EDoTHudAction`.
5. **Ввод опросом клавиш (legacy `PlayerInput`), без Enhanced Input.** Причина та же: нет ассетов.
   В M1 действия переезжают в Input Actions и Mapping Contexts.
6. **Нет DrawDebug:** все наложения (пути, круги выбора, зоны) рисует HUD, поэтому они видны и в Shipping.

## 4. Детерминизм: правила, которые держит код

- Внутри шага симуляции нет `float`/`double`. Только `Fix64` (Q32.32, int64), `FromDouble` используется лишь при загрузке контента.
- Порядок обхода везде фиксирован: массивы, сортировки с полным порядком, куча A* с тай-брейком по индексу.
- RNG: xoshiro128**, сид через splitmix64. Один поток случайных чисел на бой.
- Хэш состояния (xxHash64) снимается каждые 30 тиков и пишется в реплей. Верификатор сверяет каждый хэш.
- CI собирает `dot_runner` на `ubuntu-latest` (x86-64) и `ubuntu-24.04-arm` (ARM64),
  гоняет `--determinism 50` по трём сценариям и сравнивает вывод через `diff`.

Порядок шага: команды → ИИ → пространственный хэш → доблесть → отряды → титаны → солдаты → хэш →
вступление в бой → атаки → снаряды → зоны и отложенные удары → статусы → мораль → очистка → тела → видимость.

## 6. Что не проверено без Unreal (проверить при первой сборке)

Код UE-модуля проверен clang и gcc на заглушках API движка: синтаксис, типы, затенение имён,
экспорт символов DoTSim для модульной (DLL) сборки редактора. Реального движка в среде разработки не было,
поэтому вот допущения, которые подтвердятся только при первой сборке:

- у `/Engine/BasicShapes/BasicShapeMaterial` есть векторный параметр `Color`;
- карта `/Engine/Maps/Entry` не переопределяет GameMode;
- `AHUD::Project` возвращает Z > 0 для точек перед камерой;
- `USkyLightComponent::bRealTimeCapture` доступен для записи, а `UDirectionalLightComponent::SetAtmosphereSunLight` существует (UE 5.x);
- классы `/Script/Engine.SkyAtmosphere` и `/Script/Engine.ExponentialHeightFog` находятся через `FindObject`;
- UHT принимает forward-декларации в `namespace dot { ... }` перед `UCLASS`;
- `FDisplayMetrics::RebuildDisplayMetrics` и `TitleSafePaddingSize` (модуль ApplicationCore) отдают safe area в пикселях экрана;
- имена профилей `Android_Low/Mid/High` и `IOS` в `DefaultDeviceProfiles.ini` совпадают с профилями движка.

Если что-то из этого не так, правка локальная, в одном файле.
